# Каталог «Форель»: рабочая ветка, без публикации

24.11.2026. Рабочая ветка `catalog/forel-2026-11-24`. Рабочий сайт и main не менялись.

## Результат сверки

Исходный каталог: 200 активных карточек, включая 15 наборов и 14 алкогольных позиций. Скрытых карточек в этом источнике нет. Сохранены 200 исходных ID и 16 исторических alias; архивные источники и фотографии не удалялись. Данные источников alcohol_catalog, set_source_snapshot, source_metadata, photo_sources и deduplication изучены как связанные данные, не как дополнительные товары.

В прайсе владельца 75 строк: 17 обновлений, 48 новых карточек, 10 строк без однозначного соответствия. Всего в каталоге 248 карточек: 65 с согласованной ценой, 183 на согласовании. «Седло» требует уточнить вид мяса и не допускается к заказу. Остатки новых блюд не выдумывались: 0 до подтверждения. У новых и обновлённых блюд выход/порция/состав ресторана не подтверждены; старые веса сохранены только как reference. 1 кг в названии означает тариф за килограмм, не готовый выход мяса. Штучный сценарий по килограмму допускает целые тарифные единицы; расчёт фактического переменного веса с согласованием требует отдельной реализации до запуска такого режима.

Все 15 наборов остаются на согласовании: нет полностью подтверждённого BOM с ID/количествами/единицами/закупкой всех компонентов. 0 наборов допущены к продаже. Движок умеет пересчитывать утверждённый BOM: суммирует стоимость компонентов с количеством и один раз округляет итог. Конструктор не использует неподтверждённые цены/выходы. При отсутствии подтверждённых порций показывает причину, не придумывает состав и веса.

## Хранение закупок

Фактических закупочных сумм нет в этом документе, каталоге, клиентском JavaScript, миграциях и тестовых фикстурах. Публичный JSON хранит продажную цену и статус. Закупка поступает из серверной таблицы supplier_prices; закрытые API защищены ADMIN_TOKEN. Реальная таблица и полные отчёты подготовлены вне Git. В тестах используются отдельные синтетические цены; legacy-catalog — исторические публичные данные, не прайс поставщика.

Новая миграция drizzle/0003_supplier_prices.sql добавляет только схему и исторические снимки order_costs. Старые заказы/себестоимости не переписываются. Неизвестная себестоимость исторических заказов не превращается в нулевой расход/полную прибыль. Согласование цены требует совпадения SKU, единицы и продажной цены с целочисленной формулой. Нет повторного вычета скидки.

Порядок будущего запуска после согласования: применить миграцию и заранее загрузить подготовленный приватный SQL напрямую в серверную D1, затем публиковать код и проверить закрытый каталог. Новый закрытый POST /api/admin/pricing/import предназначен для последующих обновлений после публикации новой версии (ADMIN_TOKEN — только в заголовке; body — приватные строки product_id/cost_minor/sale_minor/unit/revision/supplier). Если код опубликован до импорта, он закрывает оформление до загрузки цен; это требует согласованного окна обслуживания. Импорт проверяет весь массив до атомарного DB.batch. До импорта закупок сервер отказывает в оформлении, даже если клиент подменит статус/цену. Это не выполненная публикация: сейчас миграция/импорт на рабочий сайт не применялись.

Для изолированного локального review: run_demo.prepare(<новый приватный путь SQLite>), затем tools/import_supplier_prices.py --input <приватный JSON вне репозитория> --local-db <этот путь>. Существующие базы клиентов автоматически не пересоздаются и не заполняются. Финансовые тесты используют отдельную копию review-базы. Локальные закупки, владельческие отчёты и SQL никогда не помещать в Git. Старый RUB-импорт блокируется на согласованном каталоге, чтобы не восстановить старые цены.
